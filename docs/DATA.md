# Data card

Everything the router, the DM and the metrics see comes from public `SKILL.md` files at pinned commits
(`skilladmit/data.py`, `SOURCES`; credits and licenses in `NOTICE.md`). Nothing is hand-labelled and nothing is
generated by a model.

## Skills (real)

- **Source**: every `SKILL.md` in 9 public repos at a fixed commit. 338 skills kept from 8 of them.
- **Router input**: the frontmatter `name` and `description`, exactly as written (markdown stripped).
- **License filter**: a skill is kept only if its own `LICENSE*` file, or else the repo license, is MIT or
  Apache-2.0 (330 MIT, 8 Apache-2.0).
- **Dedup**: first source wins on a repeated normalised name or an identical description (cross-repo copies of the
  same skill are common); descriptions under 5 words are dropped.

## Routing tasks and gold labels (DERIVED)

- A routing task is one bullet line from the skill's own "When to use" / "Use cases" / "Triggers" section,
  4-40 words, stopping at any "Do not use" / "Avoid" sub-list. Example (`wshobson/agents`, `api-design-principles`):
  *"Designing new REST or GraphQL APIs"*.
- **The gold skill of a task is the skill whose `SKILL.md` it came from.** This is a derived label: the author's
  own statement of when the skill applies, not an independent annotation of which skill a user would want.
- Dropped: bullets that are a substring of the skill's own description (trivially routable), and any bullet text
  that appears in two different skills (no single gold skill). Skills with fewer than 4 remaining tasks are dropped.
- Result: 2,102 tasks, median 6 per skill, median 7 words per task.
- Each skill's tasks are split by position: even-indexed tasks are **probe** tasks the DM may look at (an operator
  would have them as the existing routing regression suite); odd-indexed tasks are **eval** tasks. Every reported
  risk and accuracy is on eval tasks only.

## SYNTH candidates (constructed, flagged)

Lifelong streams in the main run mix real unseen skills with constructed near-duplicates of real library skills,
because real libraries do receive forks and renamed copies and the brief asks for controlled near-duplicates.
Both kinds are flagged `synth=True`, id prefix `SYNTH:`, and **own no routing tasks**: admitting one can only
steal tasks, never win any, so their value is zero by construction.

- `synth_dup`: a real base skill renamed with a suffix (`-pro`, `-helper`, ...) and 20% of its description words
  dropped at random.
- `synth_blend`: a real unseen skill's name with a suffix, description = the first sentence of a real base skill
  + the rest of the unseen skill's description.

A second run (`results/metrics_real_only.json`) uses real candidates only, no SYNTH at all.

## Streams and splits

- Per seed, the 338 skills are split into three disjoint pools of ~112 (train / calib / test). `test_iid` re-uses
  the calib pool with fresh streams (an in-distribution check of the calibration).
- One stream: 40 base skills drawn from the pool form the live library, then 24 candidates arrive in random order
  (mixed: 12 real unseen + 6 `synth_dup` + 6 `synth_blend`; real_only: 24 real unseen).
- A task is **previously correct** when the router sent it to its gold skill right after that skill was published
  (base skills at stream start, admitted candidates at admission). Misroute risk of a stream = previously-correct
  eval tasks that are wrong after the last candidate / previously-correct eval tasks.

## Known limits

- Tasks are short author-written "use when" phrases; real user requests are longer and messier.
- Gold labels are by provenance; two real skills can genuinely both fit a task, which shows up as "misroute".
- The router is a TF-IDF cosine over name+description, a CPU stand-in for the embedding or LLM selection step of a
  real progressive-disclosure agent.
